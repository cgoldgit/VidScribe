# VidScribe token 与性能检查（2026-10-08）

本文记录第一轮分析与测量；后续已实现结构化返回、程序补齐来源常量和文字缓存，第二轮测量及质量限制见 [performance_optimization_v2_2026-10-08.md](performance_optimization_v2_2026-10-08.md)。下文“仍值得进一步做”的状态保留为第一轮记录。

本轮已经修改并测试代码。最有效的方向是让写作任务一次拿到完整材料，并只携带独立写作规则。Python 准备阶段也有重复处理，但真实计时只有几十毫秒，降低模型往返比继续挤这部分更有价值。

本轮从桌面工作区当前版本开始，保留原有未提交改动。实验位于 `output/performance_2026-10-08/`。真实材料样本为 `BV1pb8o6yE8f`，约 100 分钟、2,552 句、16 包；模型对照使用另一个 13 句的合成求和演示，没有生成整片笔记或实际视频画面。

## 已实施与测量

| 改动 | 测量结果 | 实际意义与边界 |
| --- | --- | --- |
| 新增独立 `writer_system.md` | 原全片规则约 4,234 token，独立规则约 1,229，少 71.0% | 保留课堂实录、例子、事实证据、小结、广告处理、公式和来源要求；书名信息块、编号与全片操作留给控制流程。规则缩短仍需更多真实课程检验质量 |
| 可选 `--detail lean` | 16 包从 69,181 估算 token 降为 66,151，少 4.4%；126,361 字符降为 116,039 | 候选 Markdown 表改成 TSV，原句及候选定位字段仍保留。默认 compact 继续兼容 |

分词数字使用 [DeepSeek 官方 DeepSeek-V3 tokenizer](https://huggingface.co/deepseek-ai/DeepSeek-V3/blob/main/tokenizer.json)，文件 SHA256 为 `621ac2e32d0dba658404412318818aaa8ce8cda492e59830109d8da6b517fb41`。它只是统一比较尺，未确认当前供应商实际模型与此分词器相同；不含 CC 系统提示、工具定义、历史、图片或收费。安装环境本来已有 `tokenizers`，没有新增核心依赖。

将“每包规则 + 阅读包”作为同一口径的静态材料：compact + 全片规则为 136,925 估算 token，compact + 独立规则为 88,845，lean + 独立规则为 85,815。最后一项少 37.3%。该数字排除任务说明、术语、审阅模板等其他材料，不能解释为整场调用或账单少 37.3%。

## 小型实际模型对照

使用本机 CC 2.1.224 和已有供应商设置。两次独立新会话顺序执行，各最多 8 轮、1 次尝试，没有重试。两边使用同样的 13 句来源、相同事实审阅模板和相同文件权限。control 按路径读取材料并采用全片规则，improved 使用 inline 与独立规则；没有视觉候选，lean 表变化不构成这次主要差异。

这对尝试中，合计报告 token 少 84.5%，进程耗时少 55.7%。control 未正常结束，因此它是一次故障对照，不能作为同质量、正常完成任务的普遍节省比例。只有一对顺序试验，改变了规则与输入方式两项因素，不能拆分各自贡献，也没有排除供应商缓存、服务负载和随机性的影响。费用列是 CC 估算，当前供应商实际账单未核对，不能据此宣称实际支付差额。

control 的计数轮次超过所设置的 8 轮，与到达轮次限制的表现一致；旧日志只记录 `ValueError`，没有保存响应 subtype，精确失败原因无法恢复。新版本补充 `failure_code` 后可区分轮次限制、缺产物、模型错误、超时等，不需要导出原始报错。**已经生成文件的失败任务先验收，避免直接整包重跑。** 这次对 control 已有文件离线合稿成功，run 状态继续保留 failed，不把模型执行失败改写成成功。

逐句对照两份草稿，两边都保留输入 `[1, 2, 3]`、累加到 6 的过程、初始值故意写成 5 得到 11 及修复、空列表、负数 `[3, -1]`、字符串输入限制；推广句均省略，版本问题均有待核说明。优化稿保留 3 个实际大章小结。覆盖程序通过 13 句归属检查。两边都如实保持视觉 pending：control 提出 3 个待截帧，improved 根据纯口述内容暂未提出需求。该输入没有实际视频，因此这次没有证明视觉需求完整性或截图质量。个别审阅表述仍可改进，不能把结构合稿通过称为所有事实已验证正确。

## 仍值得进一步做的改进

1. **让模型返回结构化正文和审阅，由程序写文件。** 当前优化仍用 Write 工具，产生额外请求。CC 的 [`--json-schema` 与工具限制](https://code.claude.com/docs/en/cli-reference) 提供了可尝试的入口：对文字任务一次提供全部来源，模型返回草稿与审阅对象，程序校验后写到指定文件。需要验证当前供应商结构化输出兼容性、长正文的输出上限、引用转义与截断恢复；本轮没有实现或测量它。视觉任务仍需要相应图像读取能力。
2. **文本缓存改为按包内容判定。** 目前总字幕 SHA 变化会让所有旧任务失效，即使只改一处错字。可用本包原句、句子归属、时间、前后文、术语与规则共同生成缓存键，只重写变化包和受影响边界。重新绑定 source SHA 前必须证明范围对应，不能把旧审阅直接换成新 SHA。它主要改善修订和续跑，不减少首次全片阅读。
3. **把确定的机械字段交给程序。** 来源 SHA、packet_id、已验证的图片 SHA 等由任务模板可靠带入，进一步让程序补齐结果中的常量；模型主要输出章节、范围去向、真实疑点与证据。也应只回传真实边界问题，正常完成不再写多段“没有问题”的说明。范围覆盖、遗漏理由与勘误仍须由写作者判断，不能由程序猜。
4. **用包大小与有界并发调节延迟。** 当前 480 秒/6,000 字的上限可能把短章节拆成多个带规则的任务。可在实际课程上比较更大包与少量并发，记录质量、首次输出时间、总耗时、重试和真实 usage。并发本身不减少 token；无限并发、合并成一个长会话都有额外风险。本轮没有跑整片并发试验。
5. **继续按视觉用途控制输入。** 已有独立小批量和 SHA 确认复用。进一步实验应区分文字界面、代码公式、整体场景：代码公式保留清晰度，简单场景可试较小输入；发生疑点只重看相应区域/帧。需要用同一视频评估误读与漏图，不能只按图片张数或相似度删图。此次未改变图像分辨率或视觉缓存策略。

优先级是 1 → 2 → 3，再用真实课程验证 4 和 5。[Claude Code 官方成本说明](https://code.claude.com/docs/en/costs) 确认工具往返会重新携带上下文，缓存读取仍有用量与费用。本项目本轮测得的改善与这个机制一致，但单次对照没有证明每一部分成本来源。

## 验证与复现

优化后真实样本的分包计划与保存的优化前计划完全相等；16 包覆盖 2,552 句恰好一次，lean 展示逐字保留每句文本；577 项候选归属不变，包含未在概览展示的候选。`book.md`、`note_review.json`、`transcript.json` 和 `sprite_index.json` SHA256 与起始值一致。接上编辑审计后，默认成品审计为零结构错误、15 个警告：13 章缺章末小结、缺事实审阅、以及已有 20 个内容不确定项的汇总，仍为 needs_review。旧成品未改写，也没有把这些警告视为事实已正确的证明。

完整回归 **263 项通过、0 失败、1 项跳过**，结果见 `output/performance_2026-10-08/final_full_regression.log`。唯一跳过项是 Windows 当前权限下无法创建文件符号链接的实际路径测试；其他常规路径与输入保护检查已覆盖。`git diff --check` 通过。
