# 第三轮优化：完整输入、局部恢复与重复调用保护

2026-10-08，在前两轮的独立阅读包、结构化返回和已验收文字缓存之上，本轮继续减少重复输入与失败后的返工。实现没有新增运行依赖。真实字幕仍逐句、完整交给所属写作任务；事实证据、故意错误到修复的过程、画面核查和每章小结的要求继续执行。

## 开源参考与取舍

阅读官方仓库与源码，提取适合本项目的机制，没有安装或执行这些项目。

| 参考 | 与本项目相关的机制 | 本轮应用 |

| [LangGraph checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) | 持久化阶段结果，恢复时复用已成功部分 | 候选先保存并绑定输入，两个主产物落盘中断后可补齐缺失部分；不覆盖人工编辑结果 |
| [yt-scribe](https://github.com/Berkay2002/yt-scribe) | 长视频按块处理，保留块时间与来源，显式缓存和恢复 | 继续使用完整原句包与 source_ranges；把模型返回、候选验收和主产物写入分成可检查步骤 |
| [LiteLLM batch_completion 源码](https://github.com/BerriAI/litellm/blob/main/litellm/batch_completion/main.py) | 有上限的线程池执行独立请求 | 本轮先实现每任务独占锁及跨进程测试。批量并发只作为后续墙钟时间实验，尚未增加付费批量命令 |

并发本身不会减少必须处理的 token；失败重跑、重复输入和同任务重复调用更适合先处理。固定前缀有利于缓存匹配，但 CC 还会添加系统上下文，供应商是否缓存必须读实际 usage，本轮没有宣称命中。

## 已实现的行为

1. **结构化提示编译。** 标准 task.md 可可靠还原时，以完整 writer 规则、固定结构化契约、确认术语为公共前缀，随后加入包 ID、归属范围及完整阅读包。省去待填模板、文件读写与路径回传说明。完整原句、边界上下文和候选画面没有截断。人工改过的任务使用 compatibility 布局，保留完整附加要求。files 模式保持原输入契约。
2. **失败候选与本地恢复。** 字段结构合格后，先写 candidates/A001 的正文、审阅和 manifest，再核对句子覆盖、事实、小结。失败时可对照来源局部修复候选，recover-writing 全部重验后接收，不调用模型、不增加尝试。输入变化、旧尝试、错误字段、缺失事实处理和缺小结继续拒绝。
3. **明确且安全的诊断。** run.json 记录 validation.code/path，区分字段缺失、类型、覆盖重复、越界、事实和编辑问题；仅允许可信字段名与数字下标，不记录输入值、未知外部字段名、模型响应或原始错误文本。字段不合格的返回不持久化候选。
4. **同任务独占与输入再检查。** run-one、cache-writing、reuse-writing、recover-writing 共用原子创建的任务锁。第二次同任务执行在调用模型前拒绝，不同任务互不阻挡。已有 running 状态和遗留锁不自动猜测过期；模型返回后重新校验来源、任务、完整计划、归属与时长。拒绝变更结果时仍保留费用与失败用量。
5. **历史与人工成果保护。** 旧 run.json 缺 history 时，继续执行前保留上一付费快照。尝试编号须为正整数、唯一、不得超出当前尝试；当前历史记录与顶层用量、费用发生冲突时拒绝继续，避免汇总丢计数。初始未调用任务允许 0 次。恢复成功只改变当前状态，原失败历史仍参与统计；recovery.json 单独绑定当前产物和任务。之后修改产物或任务元数据会标 changed_after_recovery。半对文件只有与待恢复候选完全一致时才可补齐，人工改过的主稿不覆盖。完整内容先写同目录临时文件并 flush/fsync，再排他发布：Windows 使用目标存在即失败的 rename，POSIX 使用 link，不降级为覆盖；结构化返回、恢复和文字缓存复用共用该方式，避免人工文件恰好在检查后出现时被覆盖。

## 离线输入测量

实验使用第二轮已经准备好的真实字幕包，16 包、2,552 句。每包验证完整阅读包与完整写作规则各出现一次，并检查所有所属原句原文均在提示中。公共前缀哈希在 16 包中一致。对照旧的结构化提示布局，使用本机已有的 DeepSeek V3 分词器估算：

| 指标 | 旧布局 | 编译布局 |
|---|---:|---:|
| prompt 字符总数 | 182,887 | 160,759 |
| prompt 估算 token 总数 | 99,719 | 90,775 |
| 所属原句 | 2,552 | 2,552 |
| 阅读包 | 16 | 16 |

估算 prompt token 减少 **8.97%**。这只衡量可见文字提示，不包含 schema、CC 系统与工具上下文、历史、图片、推理输出，也不代表账单减少 8.97%。两组使用相同 schema，schema 单独记录。结果在 `output/optimization_v3_2026-10-08/prompt_comparison.json`，测量过程为同目录 `measure_prompts.py`。

对新稿逐句核对 13 句来源，正常输入与目标、初始化含义、循环、三轮变化、输出、故意错误、原因、修复、排错原则、空列表、负数和数值前提均保留；仅广告句 S000011 省略，并写明原因。小结保留具体条件和易错点。库 1.9 行为仍明示待核实，没有虚构库名或查证依据。独立计算核对结果为 6、11、修复后 6、空列表 0、负数列表 2。

发现并局部修正一处审阅表述：uncertainties 原称版本号未指明，来源实际已给出 1.9，改为版本号已给出、库名与具体行为未明确。原模型候选继续保留，未重新调用模型，也未重写正文。严格审计保留 visual_review_pending；样本没有真实视频和画面，不能宣称完成视觉验收。该库未明确，外部查证也没有可确定的目标。质量记录在 `quality_review.json`，严格审计在 `strict_sample_audit.json`。

## 使用与下一步验证

完整用法见 [B 平衡流程](balanced_workflow.md)。可选结构化模式的 inspect 会报告 compiled/compatibility、公共前缀长度及哈希；run-one 才调用模型。失败候选可用 recover-writing 在本地修复后验收，note_usage 单列恢复状态并继续统计失败尝试。
