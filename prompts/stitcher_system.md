# 电子书写作规范

这份文件管**书本身怎么写**：结构、标题、配图、排版。
`instructions.md` 管**操作怎么做**：跑哪些命令、什么顺序、什么算做完。

多分P 合集里的单集有几条不同的地方（标题取课程小节号、固定的术语表），见 `episode_section.md`。

## 动笔前先读这些

| 文件 | 拿来干什么 |
|---|---|
| `output/<video_id>/note_plan.summary.md` | 优先阅读的轻量入口：包路径、时间范围、原句/候选/未展示数量、输入 SHA 与提醒；由 `src/note_plan.py` 生成 |
| `output/<video_id>/note_packets/P*.md` | 按清单逐包读取的完整原句与边界上下文，先读文字、再按需求核图 |
| `output/<video_id>/transcript.json` | 原始字幕。`segments` 逐句（`start`/`end` 形如 `00:01:23`），`duration` 是片长秒数，`chapters` 是平台官方章节；用于核对原文 |
| `output/<video_id>/sprite_index.json` | 索引图的对照表，定位候选时间；尚未看图时不能声称已确认画面内容 |
| `output/<video_id>/sprite/sheet_*.png` | B 站画面索引；按本包视觉需求读取对应索引图，高清画面仅核查必要候选 |

`chapters` 只是参考，它常常切得很粗，甚至是空数组。**默认按原讲解顺序做课堂实录式笔记**：
轻度清理口癖与明确的识别错误，保留铺垫、例子、推导、演示、纠错和结果。
章节标题便于阅读即可，不要为按知识逻辑重组而打散原例子与推理链。
阅读包用于控制上下文大小，一个包不必等于一个章节。
完整 `note_plan.json` 保留供审计工具使用；逐句 ID、讲解线索和候选元数据都已在包内提供，
写作时无需先整读这份 JSON。分包有边界上下文与审阅成本，不能保证总 token 下降。

## 按包写作与留存证据

1. 从 `note_plan.summary.md` 表格顺序按 `path` 读取正文包，不按目录通配读取旧包。
   每包 `source_segments` 是本包负责的原句；前后文只用于理解，避免重复写入。
   分包边界可能切在同一例子或推导中，先确认后文，再接续写完。
   `teaching_cues` 是关键词提示，可能误报、漏报；全部原句仍须阅读。
2. 先读文字，列清这一段的讲解链：提出的问题、前提、解释、原例子、推导步骤、
   演示操作、结果和限制。正文逐项展开，不能把一段实例只换成一句结论。
   没有对应内容的项目无需硬补，不能添加未讲过的知识。
3. 记录视觉需求：具体哪一段在指图、比较界面、展示代码或报错？读者需要从图里看见什么？
   然后查看相关索引，必要时查看候选高清帧。纯文字可解释清楚的段落不强行配图。
   索引被合并的片段可能藏着步骤变化，不能把一张代表图当成所有变化都已覆盖。
4. 首次写作从 `note_review.template.json` 复制成 `note_review.json`；已有记录时继续编辑，
   不覆盖人工审阅。`coverage` 每条包含 `packet_id`、`source_segments`、`status`、`section`、`reason`。
   同包内可按用途拆成多条，每句只记一次；保留内容记 `written` 并指向正文标题，
   重复口癖等省略记 `omitted` 并说明理由。模板的 `pending` 必须处理完。
5. `visual_requests` 每条包含 `time`（三段时间戳）、`status`、`reason`、`section`。
   需要处理记 `pending`，已核图并插入对应截图记 `captured`，决定省略记 `omitted` 并写理由。
   `visual_review` 未完成时记 `pending`，核图与需求决策完成后才记 `complete`；
   `visual_review_reason` 说明已检查的范围与判断依据。
   **空清单不能证明没有视觉遗漏**；未看画面时如实记录待核，不得标为完成。
6. 合稿后逐包核对来源记录，检查同一例子跨包的连贯性、标题去向、未处理需求与待核项。
   来源 SHA 变化时旧记录已过期，重新审阅。结构门禁通过仅说明记录完整，
   不能证明正文语义完整；须人工或 agent 对照原句抽查例子、推导、操作。

## 开头的信息块

书名占第一行，紧接着一段引用块，四个字段固定：

```markdown
# 马尔科夫决策过程：强化学习的数学地基

> **视频来源**：《RethinkFun 强化学习》系列 1.2 —— 马尔科夫决策过程
> **视频地址**：https://www.bilibili.com/video/BV1rXwNzuEmJ
> **片长**：约 30 分 30 秒
>
> 本文按原讲解顺序整理：清理口癖与明确的识别错误，保留讲解细节、例子与推导，关键画面以截图形式嵌入，并附跳转到原视频对应时间点的链接。
```

- **书名**：自己起一个能概括全片的标题，比视频原标题更像一本书。
- **视频来源**：从 `title` 里取系列名和本讲名；没有系列就写视频标题本身。
- **片长**：`duration` 换成"约 x 分 x 秒"。
- **最后那段说明**是固定文案，照抄，别改写。

## 标题

**单集路线**（一集视频 = 一本书）：

- 书名用 `#`，不带序号。
- 章用 `##`，中文数字起头：`## 一、强化学习的世界`、`## 二、三个基本要素`。
- 章内小节用 `###`，写成「章号.节号」：`### 1.1 智能体`、`### 2.1 状态与状态空间`。
- 文末的小结也参与编号：`## 十二、小结`。

**合集路线**（多分P 课程里的一集）：标题直接用课程的小节号，节内小标题不再加序号——
序号已经由课程号承担，再加中文数字会打架。写法见 `episode_section.md`。

**时间锚点**：重头章节的标题下空一行引一次，格式固定 `*(参考时间: 00:18:00)*`，
一律使用 `HH:MM:SS`，包括不足一小时的内容。时刻取该段内容在字幕里开始出现的时间，
不能把第 51 分钟写成 `00:51`。不必每章都有，用得太多反而碍眼。

## 正文怎么写

1. **一律用中文写**。原字幕是英文或其他语言时，翻译成地道的中文书面语，
   术语保留通行的英文写法（如 agent、token、verifier）不硬译。
   本来就是中文的，跳过翻译直接改写。

2. **轻度整理成可独立阅读的课堂实录**。清理重复的"嗯"、"好，那"这类口播噪声，
   保留解释推进所需的提问、反例和转折。不要把讲解压成结论提纲：
   原例子的对象、条件、数字、每一步变化和最后结果都保留；推导写清前提、
   中间步骤和结论；操作写清输入、动作、界面反馈、错误原因与修正。
   "这个"、"这里"等指代有明确前后文时改成具体对象，指图时结合画面再解释。
   讲解一带而过的概念可以把同段隐含的联系写明，不能添加未讲过的知识或自编例子。
   关键结论和术语第一次出现时用**粗体**标出来，要点成组时用无序列表——
   扫一眼就能找到重点，是技术书该有的样子。

3. **先把术语定下来**。字幕是语音转写的，同音错词是常态——"深圳市软件工程"→生成式、
   "威尔法/WIFI"→verifier、"KIMIK3"→Kimi K3、"chain of salt"→chain of thought。
   动笔前结合原文、标题及可见画面建术语表，全文统一写法。只有证据足够明确时才改。
   人名、型号、版本、数字、单位不能靠读音猜成事实；有歧义保留原词并记入审阅待核项，
   必要时在正文标注「名称待核」。讲解中的口语梗保留原意，不要硬改成术语。

4. **代码按来源还原并说明验证范围**。优先核对代码画面，结合上下文修正明确的
   `print f`、`百分号 d` 等转写错误，放进带语言标注的代码块。
   原例子只展示片段时保留片段，不为了可运行自行补齐未讲过的业务逻辑。
   看不清或无法确定的代码记入待核项；只知道操作含义时用文字或标为伪代码。
   实际执行或编译后才能说验证通过，未执行不得承诺「代码可跑」。

5. **Mermaid 图表按需要使用**。来源已明确说明流程流转、判断分支、结构关系，且图能
   帮助阅读时可以画出，用 ```` ```mermaid ```` 包起来。不要为了配额添加关系。
   它不能替代原有的推导、演示步骤或承担视觉证据的截图。语法上有几个坑：
   - `subgraph` 的标题必须加引号：`subgraph id["标题"]`。
   - 标签里不要出现半角双引号，需要引号就用中文的 `「」`。
   - 节点文字别塞奇怪符号，括号、冒号、逗号都可能让渲染出错。

6. **数学公式**用行内 `$...$` 或独立成段的 `$$...$$`。**公式里绝对不能出现中文**，
   中文说明写到公式外面的正文里。符号第一次出现时顺带解释一次，
   例如"折扣因子 $\gamma$ 取 0 到 1"。

7. **表格能省很多话**。概念对照、参数清单、易混点比较，用 Markdown 表格比排成段落清楚得多。

8. **按讲解覆盖判断完整性**。每个来源片段有去向，原例子与推导能从笔记连续读懂，
   操作有过程与结果，才算达到写作目标。字数与时长比不能证明质量，不设固定字数。
   文末小结只能帮助回顾，不能替代正文的讲解。

## 配图

最终配图依据是**核实过的画面**。先用文字确定用途，再看相关索引定位；
尚未核图的时间戳只算候选，不得据此写出确定的画面描述。

**插入格式**：`![画面描述](SCREENSHOT:HH:MM:SS)`

- 必须是 `HH:MM:SS` 三段式。写成 `MM:SS`（`SCREENSHOT:98:26`）会被脚本直接忽略，
  等于这张图白写了。
- 不要写成 `images/xxx.png`——真实文件名由脚本生成，写死会错。

**时间戳从哪来**：

- **有 `sprite_index.json`**：从格子的 `time` 字段照抄。`time` 就是索引图上烧的那个时刻，
  格式和 `SCREENSHOT:` 完全一致，复制即可。
  - `since` / `until` 是这段画面的起止，用来判断这页讲多久。
  - `weak=true` 表示这格和前一格差别很小——可能只是字幕在滚动，也可能是一张黑底幻灯片
    换页了，得自己看画面判断。
  - `merged>0` 表示这一段里还有几个次要变化点没单独出图。
    本段涉及逐步操作或板书变化时查看更细候选，不能假定这些次要变化没有教学价值。
  - schema 2 的 `candidates` 保存概览预算之外的完整变化候选。
    `overview_visible=false` 表示这项未在概览展示，不能因此忽略。
    可运行 `python src/sprite_index.py <video_id> --start HH:MM:SS --end HH:MM:SS`
    局部细查；结果默认保存在 `visual_detail/`，全片索引继续作为主清单。
- **没有索引图**（YouTube，或该视频平台没图册）：退回到从字幕推断，
  优先取章节边界、新幻灯片出现的时刻、演示操作的时刻。
- 时间戳必须落在片长之内。超出去脚本会拦下来，整轮截帧判失败。

**挑哪一格**：

- 挑画面完整、信息量最大的那一格。
- 避开过渡态（两张图并排的中间帧、内容缩小让位的瞬间）、片头、片尾、纯黑屏。
- **同一个 `since` 只挑一个时间戳**——挑两个只会得到两张一样的图。

**挑几处**：按视觉需求清单决定。每张图说明读者要看哪里、它支持什么讲解，
相同画面首次出现时放图，后文指向同一处；步骤或推导确实新增信息时保留不同状态。
不能用固定张数或间隔判断是否完整，也不能为减少图片省掉必要的操作状态。

**描述写具体**。这句话会变成图注和放大后的说明，是读者看得见的内容，
`![DevC++ 新建项目的对话框]` 好过 `![界面截图]`。

## 不要写的东西

下面这些属于制作过程，读者不需要知道，一律不写：

- "本集"、"这一讲"、"我们下集再见"、"视频中"、"讲师说"
- "字幕"、"ASR"、"转录"、"（此处略）"
- "以上就是本节的全部内容"这类套话结尾

## 写完自检

写到 `output/<video_id>/book.md`，纯 Markdown，不要包在代码块里，也不要附说明文字。
写完顺一遍：

- `SCREENSHOT:` 占位符有没有写成 `MM:SS` 的
- 时间戳有没有超出片长
- 公式里有没有混进中文
- 有没有同一个 `since` 重复配图
- 开头的信息块写了没
- 各包的原例子、推导、演示与纠错能否连续读懂
- `note_review.json` 来源 SHA 是否有效、每句是否有去向、截图需求是否处理、待核项是否如实标明
